# Machines, materials and tools are shared, user-extensible data

**Accepted by the human (`in_561`) as proposed by the AI from `in_549` and `in_550`, with the choices of `in_556` to `in_559`. Nothing built.** The human asked how machines work, for a foundation where users can set up what is missing, and for machines and tools a user adds to be usable by others.

1. **Data versus code.** A new machine *model*, material, tool or settings table is **data**: anyone adds it, no programming. A new *process* is a **route**, which is code and a reviewed plugin. User extensions are data and templates only; code from strangers is not run (security).
2. **Definition kinds** (versioned JSON, validated, with units): *machine* (family, units, work envelope, origin, kinematics and axes, limits, G-code dialect, start and end snippets, controller capabilities, tolerance, plus route-specific fields), *material* (properties, hazards, per-process suitability, each with a source), *tool* (milling cutter, nozzle, beam: type, geometry), *settings table* (feeds and speeds; laser power and speed per thickness, keyed by machine class, material and thickness), *dialect template* (named hooks: start, end, tool change, power on and off, plus a raw custom-code escape hatch). Route-specific machine fields: FDM (nozzle, extruders, filament diameter, bed shape, chamber, maximum temperatures, volumetric flow, firmware, retraction, pressure advance); milling (spindle rpm and power, tool changer, collet, coolant, rapid rate, axes, fixtures); laser (type, power, wavelength, beam width, power scale, dynamic power, air assist, rotary); plasma, waterjet, vinyl (kerf, pierce, lead-ins). Routes ask a machine for **capabilities** ("has a 4th axis", "supports arcs"), never for its name.
3. **Presets.** Generic archetypes first ("Generic 220 x 220 Marlin printer", "Generic GRBL 3018 router", "Generic GRBL diode laser"); a few popular models as data files anyone can contribute, each editable and marked with where its numbers came from (the AI cannot verify vendor specs); user machines made by copying and overriding (`extends`). Importing Cura or Orca profile files is a later add-on, after a licence check of their data.
4. **Forgiving by design:** forms are generated from the route's parameter schema; any computed value can be overridden by hand; where data is missing the route asks and records the value, it never refuses; unknown fields are kept (an older program opens a newer definition without loss); every value carries a unit; a project stores a **copy** of the machine and material it used so it reproduces its output when presets change. **Three layers, one schema (the human approved this, `in_555`, `in_556`):** definitions are looked up in the **project copy** (a snapshot of what the project used, so old output reproduces), then the **personal library** (the user's, editable, across projects), then the **public library** (shared, versioned, trust-levelled). A personal definition can `extends` a public one; choosing one for a project copies it in; sharing is promoting a personal definition to the public library. The project and personal layers are built first; **the public layer comes later** as one more read-only source.
5. **Provenance on every definition,** as in our own docs: author, date, version, licence, `origin` (`datasheet`, `measured`, `user`), and a trust level (`official` or `user`, `in_557`). User data is flagged and never applied silently; shared entries carry a safety note where it matters (feeds and power can break a tool or start a fire; some materials give off toxic fumes).
6. **Who makes what (`in_557`, the human's decision):** keep it simple for now. **Only we make the shared (public) library of machines, tools and materials, officially, to ensure quality;** users can add their own definitions, which live in their personal library and project copies. Consequences: the trust levels reduce to `official` and `user`; there is no community contribution and no review process to run; **learning from results is not planned** (the schema may still hold a confidence count so nothing is boxed in). Exporting and importing a definition as one file (a pack) stays as a cheap way to move a user's own definitions between people; imported data is `user` data and is flagged as such. A community library and learning from results can be reconsidered later, and would be new entries. The public layer itself is built later (`in_556`) as a read-only source: a repository of JSON files served as static files, cached for offline use, versions immutable.

7. **Hazards on materials (`in_558`, approved):** an official material carries a **small structured `hazards` field**: a few flags per process (for example "do not laser cut", "needs fume extraction"), a short note and a **source** (a safety data sheet or manufacturer datasheet). A route reads the flags and raises a finding, which advises and never blocks (`in_546`). The field comes with a plain disclaimer that it is guidance and not a substitute for the material's own safety data sheet or the machine's manual. **Entries are not written from the AI's memory:** each needs its cited source and a check by whoever is responsible for the library. A user-added material carries whatever the user enters and is labelled unchecked.

8. **Tool library for the first milling version (`in_559`, approved):** the official library ships a **small starter set** of common cutters (a few flat end mills, a ball nose, a V-bit and a drill, in metric and imperial sizes hobbyists commonly own). Feeds and speeds are **advisory starting values, each with a source** (a tool maker's chart), clearly marked as a starting point; the user's own values always take priority. As with hazards, the AI does not write the numbers from memory. Users add their own cutters to their personal library. This is a promise about what ships with milling, which comes after the beam route.

9. **The material tag (`in_565`, built):** a body carries the name of its material as plain text (`scene.materials`, body name to text; command `setMaterial`; at most 60 letters; saved with the project; one step to undo). It is set from the ⋯ menu's **Material…** row (a dialog with a text box; several bodies selected are all tagged; empty takes the tag off) and shown in the Bodies list (`Body 1 · PLA`). The libraries do not exist yet, so the name is not checked against any; once they do the dialog offers their materials and a name that is in none says so (a finding, not a block, `in_546`). A copy of a body does not carry the tag yet.

## Rationale

Every machine has unique requirements and we cannot know them all (`in_550`); a user who can describe their own machine, material and tool is never blocked by our gaps. Keeping extensions to data keeps the platform safe and replaceable, and makes sharing a matter of files. Provenance and trust levels carry over our own rule that a recommendation is not a decision: a number a user typed is shown as theirs. An official-only shared library (`in_557`) keeps quality in our hands with no review process to run.
